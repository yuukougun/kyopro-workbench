## 1. 目的と方針

AtCoderの過去問精進を、Claudeとの会話を中心に支援する環境を作る。

Claudeは自動では動かず、自分が話しかけた時だけ答える。コードはClaudeに書き換えさせない。指摘は別ファイルに書き出し、自作のVSCode拡張がエディタ上に表示する。

精進の効果を落とさないことを最優先にする。ヒントは段階的に出し、完全な解法や解答コードは、ACした後か、自分が明示的にギブアップした時だけにする。ACしたかどうかは、利用者の申告で決める（Claudeは提出結果を知らないため）。

**公開リポジトリとしての方針**

- 個人の環境（フォルダの配置、絶対パス、ユーザー名）に依存する仕組みを入れない。
- 既定の設定は、リポジトリ内か、利用者がVSCodeで開いたワークスペース内で完結させる。それより外にアクセスする機能は、利用者が明示的に設定するか、その都度承認した時だけ動くようにする。
- `CLAUDE.md` や `.claude/` をどこに置くかは、各自が決める。リポジトリはテンプレートと設置用のスクリプトを用意するだけにする。
- kyopro-atlasとの連携は任意の機能にし、設定しなければ無効にする。
- ライセンスは CC0-1.0。cph fork だけは本家に従い GPL-3.0-or-later（decisions/0006）。

**対応環境**

WSL 2（Linux）を前提にする。Linux・macOSでも動く想定だが、Windowsのネイティブ環境には当面対応しない。

**名前**

| 対象 | 名前 |
|---|---|
| レビュー拡張 | ID `yuukougun.atcoder-review`（表示名 AtCoder Review）、ソースは `_extensions/atcoder-review/` |
| 設定の接頭辞 | `atcoderReview` |
| 連絡用のフォルダ | `.atcoder-review/` |
| スキルの接頭辞 | `coach-` |

VSCode拡張の一般的な規則に従う（名前は小文字とハイフン、IDは `発行者.名前`、設定の接頭辞は名前のキャメルケース）。発行者はGitHubのユーザー名にする。連絡用のフォルダは、他の道具と重ならないよう拡張の名前を付ける。スキルの接頭辞は、Claudeの役割（コーチ）から取る。ライブラリの名前空間とは揃えない。

## 2. 前提とルール上の制約

**Claude側**

公式のClaude Codeを使う。デスクトップアプリのCodeタブを推奨するが、CLIやVSCodeの公式拡張でも同じように動く。自作拡張はClaudeを一切呼び出さず、Claudeの認証情報にも触れない。

**AtCoder側**

生成AI対策ルールは、ABC/ARC/AGCの開催中にのみ適用される（Unrated参加でも対象）。過去問練習は対象外。開催中は、Claudeも、エディタのAI補完も使わない。ADT・AWCの開催中の問題も扱わない。

### 2.1 atcoder.jpのページの扱い

atcoder.jpにはAIの利用を断る指定（noai）がある。kyopro-atlasでも「AIで開かない」と決めている。これに合わせ、**Claudeは自分からはページを開かない**ことを既定にする。問題文はスクリーンショットか要約で受け取り、サンプルは `.prob` から読む。

利用者が明示した時だけ開こうとする。テンプレートの既定では、「明示」は「ページを開いて」「問題文を読んで」のように、開くことや読むことを言葉で頼んだ時を指す。「ABC123を今やってるから確認して」のように問題を伝えただけの時は開かず、スクリーンショットか要約を頼むか、開いてよいかを聞き返す。

この範囲を広げたい人（問題を伝えて確認を頼めば開いてよい、など）は、作業フォルダの `CLAUDE.local.md`（各自のファイル。install.sh は触れない）にそう書く。テンプレートの `CLAUDE.md` を書き換えないのは、install.sh で置き直した時に消えないようにするため。

開く時の動きは、権限設定で3通りに切り替えられる。

| 設定 | 明示した時の動き | 設定する場所 |
|---|---|---|
| 確認制（テンプレートの既定） | 開く前に、利用者の承認を求める | 何も書かない |
| 承認を省く | 承認なしで開く | 各自の `.claude/settings.local.json` に許可を書く |
| 禁止 | 開かない | 各自の `.claude/settings.local.json` に禁止を書く |

テンプレートの `settings.json` には、許可も禁止も書かない。禁止のルールはどの設定ファイルの許可よりも優先されるので、テンプレートに禁止を書くと、各自が `settings.local.json` で許可に変えられなくなるため。

開く場合も、Claudeに守らせることは同じ（CLAUDE.mdに書く）。

- 一度に開くのは、利用者が指定したその1問の問題ページだけ。リンクをたどって他のページを開かない。
- 解説ページは、AC後か `/coach-giveup` の後に、利用者が明示した時だけ開く。
- 取得した問題文や解説は、ファイルに保存しない。`review.json` にも問題文を引用しない。
- 拡張機能がページを先回りして取得することはしない。

READMEには、noai指定があること、既定では開かないこと、開くかどうかは各自の判断であることを書く。

## 3. 全体構成

| 構成要素 | リポジトリ内の場所 | 役割 | Claudeを呼ぶか |
|---|---|---|---|
| cph fork（既存） | `_extensions/cph-fork/` | 問題の取り込み、問題ファイル作成、サンプルテスト、提出用バンドル、テスト結果の通知（5.3） | 呼ばない |
| レビュー拡張（新規） | `_extensions/atcoder-review/` | 状態とテスト結果の書き出し、指摘と進み具合の表示、対処済みの管理 | 呼ばない |
| Claude用テンプレート | `_claude/` | CLAUDE.md、settings.json、skills。各自が作業フォルダに置く | — |
| Claude Codeのセッション | 各自の作業フォルダ | ヒント、照合、添削、質問への回答、（任意）kyopro-atlasへの記録 | 本体 |

「作業フォルダ」は、利用者がVSCodeで開いて精進に使うフォルダのこと。場所や中の配置は利用者が決める。

Claude Codeのセッションは、作業フォルダで起動したもの1つで済む。会話しながらの相談と、kyopro-atlasへの記録を同じセッションで行う（8章）。

**cph forkとの関係**

問題ファイルの作成とテスト実行はcph forkに任せる。レビュー機能はforkに組み込まず、別の拡張として作る。forkは本家へのパッチとして管理しているので、パッチを小さく保つため。forkへの追加は、テスト結果を他の拡張に知らせるイベントの公開だけにする（5.3）。forkはレビュー拡張の存在も設定も知らない。

**設計原則：各ファイルの書き手は1者だけにする。** 読むのは誰でもよい。

## 4. ディレクトリ構成とファイル仕様

### 4.1 リポジトリの構成

```
kyopro-workbench/
├── _extensions/
│   ├── cph-fork/                 # 旧 _cph。パッチ、vsix、ビルド手順
│   └── atcoder-review/           # 新規：レビュー拡張のソースと vsix
├── _claude/
│   ├── CLAUDE.md                 # テンプレート
│   ├── settings.json             # テンプレート
│   ├── skills/
│   │   └── coach-*/SKILL.md
│   └── install.sh                # 設置用スクリプト
├── docs/
│   └── dev/review-tool/design.md # 本書
├── <ライブラリ親フォルダ>/       # ライブラリ本体（名前は未定。docs/design.md）
├── include/                      # 転送用ヘッダ（自動生成・git管理外。decisions/0004, 0005）
├── .gitignore
└── README.md                     # 新規（10章）
```

先頭の `_` は、ライブラリ本体のフォルダと区別するため。

vsix（ビルド済みの拡張を1つにまとめたファイル）は、リポジトリに入れて配る。拡張を直したら、ビルドし直した vsix も一緒にコミットする。ソース（cph forkはパッチ）とビルド手順も置く。

テンプレートには、絶対パスや個人のフォルダ名を書かない。ライブラリやkyopro-atlasの場所など、環境で変わる情報は、レビュー拡張が `context.json` に書き出し、Claudeはそこから読む（4.5）。

### 4.2 install.sh

```
_claude/install.sh [--force] <作業フォルダ>
```

作業フォルダに、`CLAUDE.md`、`.claude/settings.json`、`.claude/skills/coach-*` を置く。

- 引数の作業フォルダは必須。省略した時は使い方を表示して終わり、どこにも書き込まない。
- ファイルはコピーで置く。テンプレートを直した時は、リポジトリ側で直してコミットしてから置き直す。
- 置き先にすでに中身の違うファイルがある時は、差分を表示してそのファイルを飛ばす。`--force` を付けた時だけ上書きする。
- `settings.local.json` と `CLAUDE.local.md` には触れない。

### 4.3 作業フォルダの例

配置は各自が決める。以下は一例。

```
作業フォルダ/
├── CLAUDE.md                     # install.sh で置く
├── CLAUDE.local.md               # 各自が書く（任意。2.1の範囲を広げる時など）
├── .claude/
│   ├── settings.json             # install.sh で置く
│   ├── settings.local.json       # 各自が書く（任意）
│   └── skills/
│       ├── coach-*/              # install.sh で置く
│       └── record-problem        # kyopro-atlas へのシンボリックリンク（連携時のみ・各自）
├── abc400/
│   ├── c.cpp                     # cph が作る問題ファイル
│   └── .cph/                     # cph のテストケース（.prob）
├── lib/                          # このリポジトリ（cph.bundle.includePaths は lib/include）
└── .atcoder-review/              # レビュー拡張と Claude の連絡用
    ├── context.json
    └── abc400/c/
        ├── review.json
        ├── review_state.json
        ├── last_test.json
        ├── r2.md                 # 項目の本文（あれば）
        └── r2.html               # 項目の図など（あれば）
```

作業フォルダをGitで管理する場合、`.atcoder-review/`、install.sh で置いたファイル、`CLAUDE.local.md` は管理対象から外すことをREADMEで勧める。

### 4.4 レビュー拡張の設定

| 設定 | 既定値 | 内容 |
|---|---|---|
| `atcoderReview.root` | `${workspaceFolder}/.atcoder-review` | context.json の置き場所 |
| `atcoderReview.problemDirectory` | `${root}/${contest}/${index}` | 問題ごとのファイルの置き場所 |
| `atcoderReview.atlasPath` | （空＝無効） | kyopro-atlas の場所。設定した時だけ、記録の連携を有効にする |

既定値は、開いているワークスペースの中で完結する。

変数は cph fork と同じ書き方（`${workspaceFolder}` `${contest}` `${task}` `${index}`）に `${root}` を加える。

`root` を既定から変えた場合は、`settings.json` の書き込み許可（6.3）も合わせて変える。

### 4.5 context.json

「今の状態」と「環境の情報」を表すファイル。「ここ」「今の」と言った時に、Claudeがこれを読んで対象を特定する。

```json
{
  "updatedAt": "2026-11-13T21:04:12+09:00",
  "problem": {
    "contest": "abc400",
    "task": "abc400_c",
    "index": "c",
    "url": "https://atcoder.jp/contests/abc400/tasks/abc400_c",
    "probFile": "abc400/.cph/.c.cpp_xxxx.prob"
  },
  "problemDir": ".atcoder-review/abc400/c",
  "file": "abc400/c.cpp",
  "dirty": false,
  "cursor": { "line": 23 },
  "selection": { "start": 20, "end": 31 },
  "env": {
    "includePaths": ["lib/include"],
    "atlasPath": null
  }
}
```

パスは、ワークスペース内ならワークスペースからの相対パスで書く。

`problem` の情報は、開いているファイルに対応する `.prob` から取る。`.prob` の場所は、cphの保存先の設定（`cph.general.saveLocation`）によって変わるので、cph自身と同じ方法で探す。`.prob` が見つからないファイル（ライブラリの編集中など）では、`problem` と `problemDir` を `null` にする。

`env.includePaths` は、cph forkの `cph.bundle.includePaths` を展開したもの。`env.atlasPath` は `atcoderReview.atlasPath` を展開したもので、`null` ならkyopro-atlas連携を使わない。

`dirty` は未保存の変更があるかどうか。Claudeはディスク上のファイルを読むので、`true` の時は保存を促させる。

### 4.6 書き手と読み手

| ファイル | 書き手 | 読み手 | 更新タイミング |
|---|---|---|---|
| context.json | レビュー拡張 | Claude | 選択範囲の変更（デバウンス）、保存、ファイル切り替え |
| last_test.json | レビュー拡張 | Claude | cph forkからテスト結果のイベントを受けた時 |
| review.json | Claude | レビュー拡張 | 指摘を出した時、進み具合が変わった時 |
| `<id>.md`・`<id>.html` | Claude | レビュー拡張 | 項目の本文や図を書いた時 |
| review_state.json | レビュー拡張 | Claude、レビュー拡張 | 「対処済み」をチェックした時 |
| kyopro-atlas/notes/*.md（連携時） | Claude（`/record-problem` の実行中のみ） | — | `/record-problem` 実行時 |

レビュー拡張は、Claudeが書いたファイルが読めない（JSONが壊れている）時は、エラーをパネルに表示し、直前に読めた内容を表示し続ける。

### 4.7 last_test.json

レビュー拡張が、cph forkのテスト結果のイベント（5.3）を受けて書き出す。

```json
{
  "at": "2026-11-13T21:02:40+09:00",
  "file": "abc400/c.cpp",
  "compile": { "ok": true },
  "cases": [
    { "id": 1, "verdict": "AC", "timeMs": 12 },
    { "id": 2, "verdict": "WA", "timeMs": 15,
      "input": "...", "expected": "...", "actual": "..." }
  ]
}
```

- `cases` には、その回に実行したケースだけを入れる。1ケースだけ実行した時は1件になる。
- `verdict` は `AC`・`WA`・`TLE`・`RE`・`UNKNOWN` のどれか。
- 入出力を書くのは、最初の2件の不正解のケースだけ。残りは判定だけにする。長い場合は先頭の20行・1000文字までにする。全文は `.prob` から読める。
- プログラムの標準エラー（デバッグ出力など）は書かない。大量に出ることがあり、Claude の文脈を圧迫するため。
- コンパイルエラーの内容は cph fork から受け取らないので書かない（VSCodeの出力に出る）。
- テストを実行するたびに丸ごと書き直す。

### 4.8 review.json と review_state.json

```json
{
  "file": "abc400/c.cpp",
  "progress": { "maxHint": 1, "accepted": false, "gaveUp": false },
  "nextId": 4,
  "items": [
    {
      "id": "r2",
      "line": 23,
      "endLine": 23,
      "anchor": "for (int i = 0; i <= n; i++) {",
      "kind": "bug",
      "hintLevel": 1,
      "title": "ループの終了条件をもう一度確認してみて"
    },
    { "id": "r3", "line": null, "kind": "hint", "hintLevel": 1, "title": "答えの形に注目してみて" },
    {
      "id": "r4", "line": null, "kind": "hint", "hintLevel": 2, "title": "期待値 DP で考えられる",
      "links": [{ "title": "期待値 DP", "url": "https://yuukougun.github.io/kyopro-atlas/comb/expected-value-dp/" }]
    }
  ]
}
```

`review.json` は項目の一覧で、各項目の見出し（`title`）だけを持つ。長い本文は同じフォルダの `<id>.md` に、図など Markdown で表しにくいものは `<id>.html` に書く（4.9）。`line` が `null` の項目は、行に結び付かない項目（方針のヒント・解説・別解など）。

`kind` は次の6種類。パネルではこの順に分けて並べ、ガターのアイコンの色も分ける。

| kind | 意味 |
|---|---|
| `bug` | 誤り（このままでは間違える） |
| `risk` | 誤りの可能性 |
| `hint` | ヒント（ギブアップ後の解法の説明も含む） |
| `improve` | 改善（読みやすさ・書きやすさ） |
| `alt` | 別解 |
| `library` | ライブラリ化の候補 |

`hintLevel` はその項目が明かす段階（1〜3）。段階に関係しない項目（AC 後の添削など）は書かない。`links` は関連ページ（任意。http(s) の URL だけ）で、パネルの見出しの下に並べ、閉じたままでも見える（付け方は 16章）。`review.json` の形に版は付けない（使い始めの試しの記録しかないため、古い形は捨てた）。

**進み具合（progress）**

その問題でClaudeの助けをどこまで使ったかを残す。セッションをまたいでもヒントの段階を引き継げるようにするのと、記録の `support`・`status`（8.3）の元にするため。

| 項目 | 意味 |
|---|---|
| `maxHint` | 出したヒントの最高段階（0〜3。0は使っていない） |
| `accepted` | 利用者がACしたと伝えた時（`/coach-review` の実行を含む）に `true` |
| `gaveUp` | `/coach-giveup` の実行で `true` |

解答の段階（6.1）に進んでよいのは、`accepted` か `gaveUp` が `true` の時だけ。`review.json` がない問題は、何も使っていないとみなす。

**指摘の更新のしかた**

Claudeは、毎回すべてを作り直すのではなく、必要な部分だけを書き換える。

- 新しい指摘は追加する。IDは `r<nextId>` とし、`nextId` を1増やす。IDは再利用しない。
- 内容が変わった指摘は、その項目を書き換える。IDは変えない。
- もう当てはまらなくなった指摘（コードを直して解消した、方針が変わったなど）は削除する。
- それ以外の指摘は、そのまま残す。

IDに日時を使わないのは、Claudeが今の時刻を知るにはコマンドの実行（毎回の承認）が必要になるため。`updatedAt` もClaudeには書かせず、レビュー拡張はファイルの更新を監視で知る。

`anchor` は、`line` の行の内容（前後の空白を除く）。レビュー拡張はこれを手がかりに、行のずれに追従する。

- 今の `line` の行が `anchor` と同じなら、そのまま表示する。
- 違えば、元の行から近い順に上下を探し（同じ距離なら下を優先。上に行を足すと下へずれることが多いため）、見つかった行へ範囲ごと移して表示する。
- `anchor` が短すぎる行（3文字未満や、`}` のような記号だけの行）は探さない。誤った行に移るのを防ぐため。
- 見つからなければ、ガターのアイコンは出さず（違う行を指さないため）、パネルに「見失った（元は N 行）」と出す。
- `review.json` は書き換えず、表示だけ移す（書き手は Claude だけという原則のため）。

**対処済みの管理**

パネルの各指摘にチェックボックスを付け、チェックしたら `review_state.json` に記録する。

```json
{
  "r2": { "resolved": true, "at": "2026-11-13T21:20:00+09:00" }
}
```

対処済みの指摘は、エディタ上の装飾をやめて、パネルでは薄く表示する。チェックを外せば元に戻る。

Claudeは、指摘を書き換える前に `review_state.json` を読む。対処済みの指摘を同じ内容で再び出さず、まだ直っていなければ新しい指摘として追加する。

`review.json` から消えた指摘のIDは、レビュー拡張が `review_state.json` から取り除く。

### 4.9 本文（`<id>.md`）と HTML（`<id>.html`）

ファイル名は項目の ID から決まるので、`review.json` にパスは書かない。

- `<id>.md`：パネルで見出しを開くと表示する本文。Markdown で、表、C++ のコードの色分け、数式（`$...$`・`$$...$$`）、囲み（`> [!NOTE]`・`[!TIP]`・`[!IMPORTANT]`・`[!WARNING]`・`[!CAUTION]`）、マーカー（`==...==`）、意味の決まった色（`<span class="ok|ng|key">`）が使える。任意の色は使わせない（ダークテーマでも見やすく、Claude が迷わないため）。
- `<id>.html`：決まった役割を持たせない「その他」。パネルで表しにくい時に、Claude が自由に書く。レビュー拡張に頼らず、そのファイルだけで開ける形にする。外部への通信（CDN のライブラリなど）は禁じない。
- Claude はコマンドを使わずにファイルを消せないので、項目を削除しても `.md`・`.html` は残る。ID を再利用しないので混ざらない。

## 5. 拡張の機能

### 5.1 状態の書き出し（レビュー拡張・最優先）

選択範囲やカーソルが変わった時（300ms程度のデバウンス）、保存した時、ファイルを切り替えた時に、`context.json` を更新する。

### 5.2 指摘と進み具合の表示（レビュー拡張）

**エディタ**：コードには文字を重ねない。行末の文やホバーは出さず、未対処の指摘の行のガターに、種類ごとの色のアイコンだけを出す（スクロールバーにも印を出す）。ガターのアイコンだけにホバーを付けることは、VSCode の拡張の機能ではできない（最新の API で確認）。

**パネル**（アクティビティバーに置く。ドラッグで右側のセカンダリサイドバーにも移せる）：

- 上部に問題と進み具合（使ったヒントの段階、AC、ギブアップ）、「すべて開く」「すべて閉じる」。
- 項目を種類ごとに分け、それぞれの中で行番号順に並べる（行に結び付かない項目が先）。
- 見出しをクリックすると本文を開閉する。初期状態は閉じている。開閉の状態はレビュー拡張の内部（ワークスペースの保存領域）に覚え、ファイルには書かない。
- 行番号をクリックすると、その行へ移動して一時的に強調する。
- `<id>.html` があれば「HTML を開く」ボタンを出し、押すとエディタのタブ（webview）に表示する。VSCode には HTML を表示する標準の機能がないため。HTML のファイルが変われば表示も読み直す。
- 「対処済み」のチェックボックス。
- カーソルを指摘のある行に置くと、パネルの側でその項目を強調し、見える位置までスクロールする。
- 本文の描画は webview の側で行う（markdown-it、数式は KaTeX で MathML に描くのでフォントを同梱しない、C++ の色分けは highlight.js、DOMPurify でスクリプトを取り除く）。本文の中のリンクは外部のブラウザで開く。
- `review.json` と本文・HTML のファイルを監視し、Claude が書き出したらすぐ更新する。

### 5.3 テスト結果の通知（cph forkへの追加パッチ）とlast_test.jsonの書き出し（レビュー拡張）

cph forkは、テストの実行が終わったら、その結果をイベントとして他の拡張に公開する（`activate` の戻り値で `onDidRunTests` を返す）。ファイルは書かない。全ケースを実行した時は全部終わってから1回、1ケースだけ実行した時はそのケースだけを通知する。渡す内容（ソースファイルのパス、問題のURL、コンパイルの成否、各ケースの判定・時間・入出力・標準エラー）の形は `_extensions/cph-fork/README.md` にある。

レビュー拡張は、cph forkが入っていればそのイベントを購読し、結果を `last_test.json` に書き出す。cph forkが入っていなければ、この機能は無効になる。

cph forkの判定パネルには、コンパイルエラーの文を表示する欄も足した（初期状態は閉じていて、開くと高さに上限のある枠の中でスクロールして読める。コピーのボタンつき）。コンパイルエラーは、ライブラリの中のエラーなどで極端に長くなることがあるので、`last_test.json` には入れず、必要な時に利用者が Claude に渡す。

cph forkの拡張IDは、フォークの一般的なやり方に従って自分のもの（`yuukougun.cph-fork`）にし、レビュー拡張はこのIDで探す。設定とコマンドの名前（`cph.*`）は本家のままにして、本家と入れ替えて使う（本家は無効にするかアンインストールする）。

こうすると、cph forkだけを使う人の環境に余計なファイルができず、forkへのパッチも小さく済む。

## 6. Claude用テンプレート（_claude/）

### 6.1 CLAUDE.md に書く内容

テンプレートには、特定の環境のパスを書かない。

**役割と基本姿勢**：精進のコーチであること。ソースコードとライブラリは編集しないこと。書き込んでよいのは `context.json` が示す `.atcoder-review/` 配下だけであること。例外として、利用者が `/record-problem` を実行した時だけ、そのスキルの手順に従ってkyopro-atlasの `notes/` に書き込んでよい。

**下のフォルダで起動したセッションとの関係**：Claude Codeは、起動したフォルダより上にある `CLAUDE.md` も読み込む。作業フォルダの中にライブラリや kyopro-atlas のリポジトリを置くと、そこで起動した別の目的のセッションにも、このコーチ用の指示が読み込まれる。そのため冒頭に「このフォルダより下で起動したセッションでは従わない」と書く（kyopro-atlas の `CLAUDE.md` の冒頭の注意書きと同じ形）。

**他のCLAUDE.mdとの関係**：Claude Codeは、作業フォルダの下のフォルダにあるファイルを読んだ時に、そのフォルダの `CLAUDE.md` も読み込む（kyopro-atlasの教材制作用の `CLAUDE.md` など）。精進のセッションでは、それらの指示には従わず、このファイルの方針を優先する。ただし、作業フォルダの `CLAUDE.local.md`（利用者の個人設定）は、このファイルより優先する。

**チャットとファイルの分担**：チャットは要点だけにし、中身は `review.json` と `<id>.md`・`<id>.html` に書く。チャットではどの項目に書いたかと一言の要約だけを伝える。ファイルに残るので、セッションが終わった後も見返せる。

**状態と環境の参照**：「ここ」「今の」と言われたら `context.json` を読む。`dirty` が `true` なら保存を促す。テスト結果について聞かれたら `last_test.json` を読む。

**ライブラリの読み方**：ライブラリは `env.includePaths` から探す。そこにあるのは転送用ヘッダ（`// @forward`）なので、中の `#include` が指す実ファイルを開く。`// @impl` より下は実装部分で、提出時にmainの後ろへ移動される。

**context.jsonがない時**：レビュー拡張が入っていない、まだ書き出されていないなどで `context.json` がない時は、どのファイルのどこの話かを利用者に聞く。指摘はチャットで行番号を示して伝え、ファイルには書かない。

**問題の受け取り**：問題は口頭での指定か `context.json` で特定する。問題文はスクリーンショットか要約で受け取り、ページは2.1の規則に従って、利用者が明示した時だけ開く。開催中のコンテストの問題は扱わない。

**kyopro-atlas連携（`env.atlasPath` がある時だけ）**：教材の `claude/explain.md` の「教材から探す」の手順でページを引き、根拠のページの公開URLを示す。用語と記法は教材に合わせる。連携していない時は、一般的な知識で答え、手法の名前の扱いはヒント段階に従う。`/record-problem` が実行された時は、それまでの会話と `review.json` の進み具合から、原因・学んだこと・関連ページ・助けを使った段階などの案を出し、利用者に確かめてから記録する。

**ヒント段階**：

| 段階 | 内容 |
|---|---|
| Lv1 | 気づくべき点を1つ示す。手法の名前は出さない |
| Lv2 | 手法の名前を出す（連携時は根拠のページのURLも） |
| Lv3 | 方針、正しさ、計算量、実装の要点 |
| 解答 | 完全な解答コード。`progress.accepted` か `progress.gaveUp` が `true` の時のみ |

段階を指定されなかったら、これまでの最高段階（`progress.maxHint`、初回はLv1）から始める。利用者が「分からない」と言った、前のヒントの点がまだ直っていないなど、その段階では進めない様子なら、Claudeの判断で1段ずつ上げてよい。上げる時は「Lv2に上げる」のように一言添え、2段以上を一度に上げない。Claudeの判断で上げられるのはLv3までで、解答には進まない。ヒントを出したら `progress.maxHint` を更新する。利用者がACしたと伝えたら `progress.accepted` を `true` にする。Lv1とLv2はkyopro-atlasの「ヒントだけ」、Lv3は「解説まで」に対応する。

**原因の一言**：ヒントや解説を使った時、または解けなかった時は、最後に原因を4つ（知識不足／気づけなかった／実装ミス／時間不足）から1つ選んで添える。ヒントの段階では、原因も手がかりになるので、解けた後に添える。自力でACした時は添えない。分類はkyopro-atlasと同じ。

**`/record-problem` の中での注意**：作業フォルダから呼んでも、記録の手順の中では atcoder.jp を開かない。会話で開いた問題文や解説の文章を `notes/` に写さず、`memo`・`learned` は自分の言葉で書く。

**その他**：各ファイルの形式（4章）、review.jsonの更新のしかたと対処済みの扱い（4.8）。

### 6.2 skills

名前に共通の接頭辞 `coach-` を付ける。入力欄で `/coach` と打つだけで、このスキルだけに絞り込めるようにするため。

| コマンド | 内容 | Claudeが自分で使えるか |
|---|---|---|
| /coach-hint [段階] | 指定段階のヒントを出す。段階を省くと、今の段階からClaudeが判断する（6.1）。指摘があれば review.json を更新する | 使える |
| /coach-check | 問題文と実装を照らし合わせ、制約の範囲、型、境界、出力形式、計算量の食い違いをピンポイントで指摘する | 使える |
| /coach-review | ACの申告を兼ねる。添削と別解を出し、review.json を更新する | 使えない |
| /coach-giveup | ギブアップを宣言する。解答の段階に進めるようにする | 使えない |

`/coach-review` と `/coach-giveup` には `disable-model-invocation: true` を付け、利用者が打った時だけ動くようにする。Claudeが自分の判断で解答の段階に進まないようにするため。

記録には、kyopro-atlasの `/record-problem` をそのまま使う（8章）。記録用のスキルをこのリポジトリでは作らない。

スキルの `description` は、`/` のメニューに出る説明なので、短く具体的に書く。引数があるものは `argument-hint` を付ける。

### 6.3 権限（settings.json）

既定の権限の動き（ファイルの編集やシェルコマンドの前に確認が出る）を前提に、次のように設定する。

- `.atcoder-review/` 配下への書き込みは、確認なしで許可する。
- kyopro-atlas の検索（`.claude/skills/record-problem/record_tool.py` の `pages`・`url`）は、確認なしで許可する（16章）。
- ソースファイルとヘッダ（`*.cpp`、`*.hpp`、`*.h` など）の編集と新規作成は禁止する。この禁止は、`Edit` と `Write` のほか、Claude Codeが認識するシェルのファイル操作（`sed`、`tee`、リダイレクトなど）にも効く。
- シェルコマンドは広く許可しない。PythonやNodeのスクリプトの中でファイルを開いて書き換える操作は、上の禁止では防げないため。毎回確認が出る状態にしておく。OSのレベルで確実に防ぎたい人は、Claude Codeのサンドボックスを使う。
- kyopro-atlasの `notes/` への書き込みは、テンプレートでは何も書かない（書き込むたびに確認が出る）。確認を省きたい人は、各自の `settings.local.json` で許可する。
- atcoder.jpの取得は、テンプレートでは何も書かない（2.1）。

特定のフォルダ名やパスに依存するルールは入れない。具体的な記法は、実装時に公式ドキュメントで確かめる。

## 8. kyopro-atlasとの記録の連携（任意）

### 8.1 方針

kyopro-atlasの記録スキル `/record-problem` を、作業フォルダのセッションからそのまま使う。会話の流れと `review.json` の進み具合を知っているセッションで記録するので、原因や学んだことをClaudeが案として出し、利用者は確かめるだけで済む。

そのために、次の2つを行う。

1. `/record-problem` を、どのフォルダで起動しても動く書き方にする（kyopro-atlas側の変更、8.3）。
2. 作業フォルダの `.claude/skills/` に、kyopro-atlasのスキルへのシンボリックリンクを置く（各自の設定、8.2）。

### 8.2 スキルの登録（各自の設定）

```
ln -s <kyopro-atlas>/.claude/skills/record-problem <作業フォルダ>/.claude/skills/record-problem
```

kyopro-atlas が作業フォルダの外にある場合は、`notes/` への書き込みのたびに作業フォルダの外への承認を求められる。避けたい人は、各自の `settings.local.json` の `additionalDirectories` に kyopro-atlas の `notes/` を足す。`record_tool.py` は PyYAML を使うので、入っていなければ入れる。

コピーではなくリンクにするのは、スキルが補助スクリプト（`record_tool.py`）と一緒に動くことと、kyopro-atlasを更新した時に自動で追従させるため。個人の環境に依存する設定なので、install.sh では行わず、READMEに手順を書く。

kyopro-atlasを作業フォルダの中に置いていても、その `.claude/skills/` は、Claudeがkyopro-atlasのファイルを読むか編集するまで読み込まれない。最初から `/` のメニューに出すため、リンクで明示的に登録する。

### 8.3 kyopro-atlas側の変更

**どこで起動しても動くようにする**

今の `/record-problem` は、リポジトリの根で実行される前提で、補助スクリプトと `notes/` を相対パスで扱っている。これを次のように直す。

- `record_tool.py` に、リポジトリの根を出力する機能（例：`record_tool.py root`）と、`tools/ap.py` を代わりに呼ぶ機能（例：`record_tool.py ap show <ID>`）を加える。`ap` で通すのは `show`・`contest`・`fetch` だけにし、`allowed-tools` で許す範囲を狭く保つ。`record_tool.py` と `tools/ap.py` は、どちらもすでに `Path(__file__).resolve()` で実体の場所から根を求める作りなので、シンボリックリンク経由で呼ばれても実体のリポジトリを指せる。
- スキルの本文と `allowed-tools` のコマンドは、`python3 ${CLAUDE_SKILL_DIR}/record_tool.py …` の1種類だけにする。`${CLAUDE_SKILL_DIR}` は `allowed-tools` のBashのルールの中でも展開される。`tools/ap.py` を直接呼ばないのは、その絶対パスが環境ごとに違い、`allowed-tools` に書けないため。
- `notes/` の書き込み先と、本文で読ませるファイル（`claude/record-format.md` など）は、`record_tool.py root` の出力を基準にした絶対パスにする。
- 作業フォルダの外から呼ばれても、`/record-problem` の中では atcoder.jp を開かない。開いて得た問題文や解説の文章を `notes/` に写さない。
- kyopro-atlas の `CLAUDE.md` に、外のセッションから読み込まれた時の注意書きを足すかは、kyopro-atlas のセッションが利用者に確かめて決める。

`${CLAUDE_SKILL_DIR}` がリンク側と実体側のどちらのパスになるかは公式ドキュメントに書かれていないが、どちらでも `record_tool.py` に届き、根は実体側から求まるので、この書き方なら影響しない。

kyopro-atlasのフォルダで使う時の動きは変わらない。

**記録形式の追加項目（record-format v2）**

| 項目 | 値 | ないとき | 元にする情報 |
|---|---|---|---|
| `support` | `自力`・`ヒントだけ`・`解説まで`・`ギブアップ` | null | `progress`：`gaveUp` なら `ギブアップ`、`maxHint` が3なら `解説まで`、1〜2なら `ヒントだけ`、0なら `自力` |
| `status` | `AC`・`未AC`（その記録の時点の状態。records の1件ごとに持つ） | null | `progress.accepted` |
| `code` | 作業フォルダからの解答ファイルのパス（kyopro-atlas 側ではただの文字列として扱う） | null | `review.json` の `file` |

どれも任意の項目にし、分からなければ書かない（null も書かない）。v1 の記録もそのまま通す。`support` は使った助けのうち最も強いもの（自力 < ヒントだけ < 解説まで < ギブアップ）、`status` の今の状態は null でない最後の記録の値で見る。値の名前は kyopro-atlas の解説役の言葉（「ヒントだけ」「解説まで」）にそろえる。claude.ai の解説から出す記録用まとめでは、`code` は常に null、`status` は利用者がACしたと言った時だけ `AC` にする。`support` は原因（なぜ解けなかったか）とは別に、どこまで助けを使ったかを残す。`status` は解き直しが必要な問題を後から探しやすくする。`code` は記録から自分の実装をたどれるようにする。

**合わせて直すファイル**

kyopro-atlasの規則に従い、形を変える時は版を上げ、関係するファイルを合わせて直す。

| ファイル | 変更 |
|---|---|
| `.claude/skills/record-problem/SKILL.md` | どこで起動しても動く書き方にする。v2の項目を notes に書く |
| `.claude/skills/record-problem/record_tool.py` | `root` と `ap`（show・contest・fetch のみ）の機能を加える。`check` にv2の項目の値の検査を加える（v1 の記録も通す） |
| `claude/record-format.md` | v2の項目を追加する |
| `claude/explain.md` | 記録用まとめをv2の形で出す |

### 8.4 実装時に確かめること

- `/record-problem` は `disable-model-invocation: true` のままにし、会話の途中でClaudeが勝手に記録しないこと。
- kyopro-atlasのファイルを読んで、その `CLAUDE.md`（教材制作用）が読み込まれても、作業フォルダの `CLAUDE.md` の方針が優先されること。

## 9. 運用フロー（1問の流れ）

Competitive Companionで問題を取り込むと、cph forkが問題ファイルとテストケースを作る。

VSCodeでコードを書き、cphでサンプルを確認する。テスト結果は自動で `last_test.json` に残る。

詰まったら、該当箇所を選択したまま保存し、Claude Codeで「ここ見て」や `/coach-hint 1` と話しかける。問題文はスクリーンショットか要約で渡す。WAの原因が分からない時は `/coach-check` を使う。指摘はエディタ上と右パネルに表示され、直したら対処済みにチェックする。

ACしたら `/coach-review` で添削と別解を受ける。解けずに諦める時は `/coach-giveup` で解答を見る。kyopro-atlasと連携している場合は、記録を残したい問題で、そのまま同じセッションで `/record-problem abc400_c` を実行する。Claudeが会話と進み具合から記録の案を出すので、確かめて記録する。

**セットアップの手順**

1. リポジトリにある cph fork とレビュー拡張の vsix をインストールする。本家の cph は無効にしておく。
2. `_claude/install.sh <作業フォルダ>` で、テンプレートを作業フォルダに置く。
3. cph fork の `cph.bundle.includePaths` などを、自分の環境に合わせて設定する。
4. 必要なら、`.claude/settings.local.json` で atcoder.jp の取得の承認を省くか、禁止する。開いてよい場面を広げたい時は、`CLAUDE.local.md` に書く。このファイルを手で作った場合は、各自で .gitignore に加える（Claude Code が自動で git の管理から外すのは、Claude Code 自身がこのファイルを作った時だけ）。
5. kyopro-atlas と連携する場合だけ、`atcoderReview.atlasPath` を設定し、`/record-problem` へのシンボリックリンクを作業フォルダの `.claude/skills/` に置く（8.2）。
6. Claude Codeで作業フォルダを開く（デスクトップアプリならWSLセッションで）。

## 15. 使ってみてからの改善

最初の実装を利用者が使ってみて、次のように改めた（議論の経過は `docs/discussions/2026-11-13_review-tool.md`）。

| 改めたこと | 理由 |
|---|---|
| エディタの行末の文とホバーをやめ、ガターのアイコンだけにした | 実装とコメントがコードの中に混ざって見づらい |
| パネルを Markdown で描き、図などは HTML のタブで開けるようにした | 文字だけでは分かりにくい。数式や表、強調を使いたい |
| 本文を `<id>.md`・`<id>.html` に分け、行に結び付かない項目も置けるようにした | JSON の中の長い文はエスケープで書き損じやすい。方針や解説もファイルに残して見返したい |
| 項目に種類（kind）を付けた | 種類ごとに分けて見たい。ライブラリ化の候補を拾ってライブラリ作りにつなげたい |
| 見出しの開閉（初期状態は閉じる） | 一覧を見渡しやすくする |
| 行のずれに追従するようにした | 直すたびに表示がずれるため |
| カーソルのある行の項目をパネルで強調するようにした | ガターのアイコンだけにホバーは付けられないので、その代わり |
| cph fork の判定パネルにコンパイルエラーの欄を足した | エラーの文を見て Claude に渡しやすくする |

## 16. 使用量の見直し

利用者は何問も続けて解くので、要らないものを読んだり書いたりして使用量を増やさないようにした（必要なものは惜しまない）。

| 対策 | 内容 |
|---|---|
| 1問ごとに会話を区切る | `context.json` の問題が変わったら、Claude が一度だけ `/clear` を勧める（記録するなら先に `/record-problem`）。進み具合や指摘はファイルに残る。一番効果が大きい |
| 教材の調べ方を軽くする | kyopro-atlas の索引（`llms.txt` 約7.6万字）やページの本文は読まず、`record_tool.py pages --limit 3` を1項目1回だけ使う（出力は3行）。本文は利用者が「詳しく」と頼んだ時だけ1ページ読む |
| ライブラリを読む範囲 | 問題がその部分に関係しそうな時だけ読む |
| `last_test.json` を小さくする | 入出力は最初の2件の不正解だけ（20行・1000字まで）。標準エラーは書かない |
| 書きすぎない | 本文は必要な分だけ。HTML は図などがはっきり役立つ時だけ |

確かめて問題なかったもの：コーチ用の CLAUDE.md（約7千字。毎回の応答で使うので分けても減らない）、スキルの本文（打った時だけ読み込まれ、どれも1千字前後）、`context.json`・`review.json`・cph のテストケース（1問約700バイト）、`/record-problem`（1回の記録で約6〜9千字。kyopro-atlas のセッションも許容範囲と判断）。

### 教材のリンクの付け方（kyopro-atlas のセッションと合意）

- 付けるのは Lv2 以上の項目、AC 後の添削、ギブアップ後だけ。Lv1 では付けない（ページの題名が手法の名前なので答えを明かす）。要らないリンクは付けない。
- 検索は部分一致なので、題名が項目の手法と合うものだけを付ける。合わなければ付けない。状態が `done` のページだけ。
- `--problem` で出る台帳のページは解き方そのものなので、Lv2 ではヒントで出した手法に合う1件だけ。全部を付けてよいのは Lv3・AC 後・ギブアップ後。
- `pages`・`url` の引数と出力の形は kyopro-atlas 側で固定し、変える時は先に知らせてもらう。
