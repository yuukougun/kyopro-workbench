## cph の include 展開について

### 再帰展開されるか
- されている（`_cph/cph-fork.patch` の `src/bundler.ts`）。3段の入れ子 include で動作を確認済み。
- 探す順: include しているファイルのフォルダ → `cph.bundle.includePaths`。
- 同じファイルは1回だけ展開、循環 include も検出して止まる。`#pragma once` / include guard は除去。
- `// @impl` より下は提出コードの末尾にまとめて出力される。
- 細かい注意点（実害は小さい）:
  - `#ifdef LOCAL` 内で先に include したファイルを、後で条件外でも include すると2回展開される。
  - `/* */` ブロックコメント内の `#include "..."` も展開されてしまう。

### 使った関数・クラスだけを展開するか
- 提案: シンボル単位の削減はしない。展開はファイル単位のままにする。
  - C++ の解析（テンプレート、オーバーロード、マクロ、演算子、メンバ関数）が必要で、壊れたコードを出すと本番で致命的。
  - 未使用のコードがあっても害は小さい（AtCoder のコード長制限は 512KiB）。
- 代わりに「1ファイル1機能」で細かく分け、依存は include で表す。これでファイル単位で「使うものだけ」展開できる。
- 状態: 採用 → decisions/0001

## 前提と基本方針
- AtCoder 用、C++ は cph の設定（`g++-15 -std=gnu++23 -O2`）、ACL は使わない、`using namespace std` 前提、自作名前空間は1つ、汎用性は高め → decisions/0002
- main を上に保つため、原則すべてで `// @impl` を使う → decisions/0003
  - 定義を main の後ろに置いても、テンプレートはコンパイルできることを確認した。戻り値 `auto` の関数は不可。
- cph: 改善したいのは `/* */` 内の include。`// #include` はもともと展開されない（展開されるのは行頭が `#` の行だけ）。

## 置き場所と include の書き方
- 名前空間と親フォルダの名前は保留。親フォルダ1つにまとめ、その下の階層の深さは固定しない。
- VSCode の設定例はリポジトリで管理しない。
- include はファイル名だけで書きたい（例: `#include "segtree.hpp"`）。
  - cph のテスト実行は展開前のコードを `g++ -I lib` でコンパイルするので、展開処理だけでなく g++ もファイル名で見つけられる必要がある。
  - 提案: 全ヘッダへのシンボリックリンクを1つのフォルダ（例 `include/`）に自動生成し、includePaths と `-I` をそこに向ける。
    - g++・cph の展開・`@impl` がすべて動くことを試作で確認した（3階層 + ライブラリ同士の include）。
    - ファイル名はライブラリ全体で重複禁止。生成スクリプトで重複を検出する。
  - 状態: 提案中
- 追記（ヘルパー・util を踏まえて再検討）:
  - シンボリックリンクだと、リンク経由で開いたヘッダ内の相対パス include（`"internal/node.hpp"` など）を g++ が見つけられない（試作で確認）。
    → 中身が `#include "../kp/.../segtree.hpp"` の1行だけの転送用ヘッダを生成する方式に変更。g++・cph の展開・`@impl` とも動作確認済み。
    → 展開後に begin/end のコメントが二重になるので、cph 側で転送用ヘッダは目印を省くと見やすい。
  - ファイル名の重複禁止は、回答コードからファイル名で include する「公開」ファイルだけでよい（1つの名前は1つのファイルにしか転送できないため）。
  - ファイルを3種類に分ける案:
    - 公開ライブラリ（segtree など）と公開ユーティリティ（chmin、デバッグ出力、入力補助など）: 転送用ヘッダを作る。名前は重複禁止。
    - 内部ヘルパー（ライブラリからだけ使う）: `internal/` フォルダに置き、相対パスで include。転送用ヘッダは作らず、名前の重複も可。
  - 状態: 提案中
- 決定: 転送用ヘッダ方式、`include/` 内の階層は最大3、ヘルパー・util の置き場所は自由、`include/` はコミット → decisions/0004
- 次の論点: 各ファイルの include 名をどう決めるか（提案: ファイル冒頭の `// @export` 注釈）
- 決定: 回答コードは `include/` のものだけを include し、`-I` は `include/` のみ → decisions/0004 に追記
- 決定: include 名は `// @export` 注釈で決める → decisions/0005
